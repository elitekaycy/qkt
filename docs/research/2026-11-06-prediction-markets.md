# Prediction markets: venues, mechanics, and fit with qkt

**Research, 2026-11-05/06.** Source notes for the designs in `docs/superpowers/specs/2026-11-06-event-contracts-design.md`,
`2026-11-06-symbol-sets-and-universes-design.md` and the gateway plan `qkt-venue-gateway/docs/plans/2026-11-06-event-contracts-and-kalshi.md`.
Venue facts were checked against live public APIs and docs on 2026-11-05; re-check before building, these venues changed a lot in 2026.


Yes, Kalshi and Polymarket can both be traded through qkt, and the first version needs no qkt core change. A `qkt-venue-gateway` adapter can list each binary market as an ordinary `spot` instrument and report a resolution as a VGP `settlement` at price 0 or 1. qkt already closes every holder of a settled symbol whatever its kind, so P&L comes out right. Only three things in qkt core block a clean model: a settlement price of 0 is refused, zero-price ticks are dropped, and there is no fee model shaped like p(1−p). Each is a one-file change. A proper `event` instrument kind is worth building later, but it touches about 23 files plus the VGP spec, so it should wait until a strategy has proved itself. Choose the venue by access before ease of build. Kalshi has the cleaner API for the gateway's rules: a client order id, a demo environment, decimal strings and a published fee formula per series. But nobody has checked whether a Ghana resident can open a Kalshi account. Polymarket's international venue does not geoblock Ghana, but its adapter is much harder: EIP-712 signing, on-chain redemption, asynchronous settlement, and no confirmed order label the gateway can look orders up by. The evidence for an edge is structural, not predictive. Makers beat takers, and favourites beat longshots, in two independent large Kalshi datasets. Forecast-driven bots, weather bots included, have no audited record and trade against a market that already beats the public forecast. The plan is to verify eligibility first, build a Kalshi data pipeline outside qkt that needs no account, backtest a favourite-carry strategy, then write a `spot`-kind Kalshi adapter. If Kalshi turns out to be closed to Ghana, Polymarket takes its place.

## Two venues, two very different engineering problems

**Kalshi is a CFTC-regulated exchange with a conventional REST, WebSocket and FIX API, and in 2026 it moved to fixed-point strings and a single-book order model.** Production REST is at `https://external-api.kalshi.com/trade-api/v2` and the demo is at `https://external-api.demo.kalshi.co/trade-api/v2`. Each request is signed with RSA-PSS-SHA256 or Ed25519 over `timestamp_ms + METHOD + path`, with the query string excluded ([API Keys](https://docs.kalshi.com/getting_started/api_keys)). Orders go to V2 `POST /portfolio/events/orders` with `side: bid|ask` on the YES leg, a dollar-string price, a fixed-point `count`, `good_till_canceled|immediate_or_cancel|fill_or_kill`, a required self-trade-prevention type, and an optional **`client_order_id`**. There is **no market order type**, and `reduce_only` is accepted only with IOC ([Create Order V2](https://docs.kalshi.com/api-reference/orders/create-order-v2.md)). The legacy `/portfolio/orders` mutations were deprecated in June 2026, so anything copied from older code is wrong ([Changelog](https://docs.kalshi.com/changelog/index.md)). A position is **one signed number per market, positive for YES and negative for NO** ([Get Positions](https://docs.kalshi.com/api-reference/portfolio/get-positions.md)). The REST orderbook returns bids only on each side, so the best YES ask is 1 minus the best NO bid ([Orderbook Responses](https://docs.kalshi.com/getting_started/orderbook_responses.md)). Rate limits start at 200 reads and 100 writes per second on the Basic tier, and FIX 5.0SP2 order entry without retransmit is available without gating ([Rate Limits](https://docs.kalshi.com/getting_started/rate_limits); [FIX Connectivity](https://docs.kalshi.com/fix/connectivity.md)).

Three 2026 details change what an adapter has to handle. The exchange is **split into four shards** (0 default, 1 combos, 2 crypto and commodities, 3 some sports), and capital is held per shard ([live exchange status](https://external-api.kalshi.com/trade-api/v2/exchange/status)). **Sub-cent ticks** come from per-market `price_ranges` bands, and the exchange rejects any price off the grid. Whole cents are valid in every structure, so a qkt tick of 0.01 is always safe. And **fractional contracts** (0.01 granularity) are enabled on some markets: a live weather book showed a resting level of 27.29 contracts. Fractional fills can arrive even on orders for whole contracts ([Fixed-Point](https://docs.kalshi.com/getting_started/fixed_point_migration.md); [live orderbook](https://external-api.kalshi.com/trade-api/v2/markets/KXHIGHNY-26NOV06-T67/orderbook)). The adapter must therefore report fractional fill quantities, and the instrument's `volume_step` should be 0.01, not 1.

**Polymarket's international venue matches orders off-chain and settles them on Polygon, so a trade is a signed EIP-712 message, not an API call with a key.** API credentials come from an L1 EIP-712 wallet signature, and REST calls are then authenticated with L2 HMAC-SHA256 ([Wallets & Auth](https://docs.polymarket.com/trading/wallets-auth.md)). The order struct is `salt, maker, signer, tokenId, makerAmount, takerAmount, side, signatureType, timestamp, metadata, builder`. The EIP-712 domain version and verifying contract change with the book: V2 markets use "3" and `0xe333…00Aa`, CTF non-negRisk markets use "2" and `0xE111…996B`, and CTF negRisk markets use "2" and `0xe222…0F59`. Deposit Wallets, the default since May 2026, add ERC-7739 `TypedDataSign` wrapping. Plain EOA trading needs an allowlisted address ([Place Orders](https://docs.polymarket.com/trading/place-orders.md)). The 2026-04-28 CLOB V2 cutover replaced the exchange contracts, swapped USDC.e collateral for **pUSD**, wiped every open order, and stopped accepting V1-signed orders. The legacy `py-clob-client`, `clob-client` and `rs-clob-client` repos are archived ([Changelog](https://docs.polymarket.com/changelog)). There is **no official Java or Kotlin client**, so a JVM adapter must implement the signing itself (web3j can do the EIP-712 and secp256k1 parts), or wrap `rs-clob-client-v2` or `py-clob-client-v2` in a sidecar ([GitHub Polymarket org](https://github.com/Polymarket)).

Polymarket's lifecycle is also asynchronous in a way Kalshi's is not. A match is provisional: trade status moves through `MATCHED`, `MINED` and `CONFIRMED`, and it can end in `FAILED`. The user WebSocket has **no replay after a disconnect**, so open orders and trades must be re-fetched over REST ([Real-Time Order Updates](https://docs.polymarket.com/trading/realtime-order-updates.md)). Winning shares do not turn into cash on their own: redemption is an on-chain call through the relayer or a contract. The kill switch fits well, though. A heartbeat dead-man switch queues a cancel-all after 10 seconds of silence, and there is no way to disarm it ([Manage Orders](https://docs.polymarket.com/trading/manage-orders.md)).

| | Kalshi | Polymarket (international) |
|---|---|---|
| Regulator | CFTC DCM | Unregulated offshore; a separate US DCM exists |
| Auth | RSA-PSS or Ed25519 request signing | EIP-712 wallet (L1) plus HMAC (L2); every order signed |
| Client order label | `client_order_id` on create | None confirmed; struct has `salt`, `metadata` |
| Test environment | Full demo REST, WS and FIX | None found |
| Order types | GTC, IOC, FOK, post-only; no market, no stop | GTC, GTD, FAK, FOK, post-only; no stop |
| Position model | One signed position per market (short = NO) | Separate YES and NO tokens, long-only |
| Tick | Per-market bands, $0.01 to $0.0001 | Per market, 0.1 to 0.0001 |
| Fee | Taker `ceil(M·0.07·C·P·(1−P))`; maker 0.0175 on some series | Taker-only `C·rate·p(1−p)`, rate 0 to 0.07; makers get rebates |
| Resolution | Kalshi, from a named source; review process for disputes | UMA optimistic oracle (2h, 4–6 days if disputed); Chainlink TWAP for crypto up/down |
| Cash after resolution | Automatic | On-chain redeem |
| History | Free 1m/1h/1d bid-ask candles plus trades | Price series back to 2022 plus trades; on-chain fills |

The fees decide which strategies can work. Kalshi charges takers `round_up(M × 0.07 × C × P × (1−P))`, which peaks at 1.75 cents per contract at 50 cents. Makers pay only on series whose `fee_type` is `quadratic_with_maker_fees`, at a quarter of the taker rate. A live probe on 2026-11-05 found that weather, S&P and BTC series are plain `quadratic` with multiplier 1, while NFL and NBA game series charge makers, and MLB uses multiplier 0.5. An adapter can therefore compute fees exactly from `GET /series/{ticker}` ([live series](https://external-api.kalshi.com/trade-api/v2/series/KXMLBGAME); [Prediction Hunt fee guide](https://www.predictionhunt.com/blog/kalshi-fees-complete-guide-2026)). The official fee PDF returned HTTP 429, so the effective date and any settlement fee are still unverified. Polymarket has charged **taker-only fees on almost every category since 2026-03-30**: crypto 0.07, sports 0.05, politics and finance 0.04, geopolitics 0. Each market carries its own `feeSchedule`, and makers receive 15–25% of taker fees back as rebates ([Polymarket Fees](https://docs.polymarket.com/trading/fees.md)). Both venues scale fees by p(1−p), so **fees are smallest at the extremes and largest at 50 cents**. That rewards strategies that rest orders and trade favourites, and it punishes taker strategies that trade mid-priced contracts.

## Series, events and strikes become qkt symbols without parsing tickers

**Kalshi's hierarchy is Series → Event → Market, and every field needed to know what a market pays on is structured. Kalshi explicitly says not to parse tickers** ([Kalshi Glossary](https://docs.kalshi.com/getting_started/terms.md)). The series (`KXHIGHNY`) carries the category, frequency, settlement source, `fee_type`, `fee_multiplier` and contract terms PDF ([live series](https://external-api.kalshi.com/trade-api/v2/series/KXHIGHNY)). The event (`KXHIGHNY-26NOV06`) carries `mutually_exclusive`, `strike_date` and `collateral_return_type`. Each market carries `strike_type` (one of `greater`, `greater_or_equal`, `less`, `less_or_equal`, `between`, `functional`, `custom`, `structured`) with `floor_strike` and `cap_strike`, the human label `yes_sub_title`, `close_time`, `expected_expiration_time`, `latest_expiration_time`, `status`, `result`, `settlement_value_dollars`, `price_ranges` and `exchange_index` ([Get Market](https://docs.kalshi.com/api-reference/market/get-market.md)). Turning that into a machine-readable predicate is mechanical. A market's YES pays $1 × `notional_value_dollars` when the event's `expiration_value` satisfies the strike predicate. `greater` and `less` are strict. `between` is inclusive at both ends: the live `between 73–74` market is labelled "73° to 74°".

Events come in two shapes, and each supports a different kind of strategy. A **mutually exclusive event partitions the outcome space**. The live NYC-high event for 2026-11-06 had six markets: `T67` "66° or below", four two-degree `B` buckets (B67.5, B69.5, B71.5, B73.5, each code being the bucket midpoint), and `T74` "75° or above". Exactly one resolves YES, so the YES asks should sum to at least $1, and the sum is a direct measure of the overround ([live event](https://external-api.kalshi.com/trade-api/v2/events/KXHIGHNY-26NOV06)). A **ladder event** (`mutually_exclusive: false`), such as `KXFED-26DEC` or the hourly S&P `KXINXU`, is a set of nested digital calls ("above 6.00%", "7,425 or above"). Adjacent strikes can be differenced into synthetic range bets ([live KXFED](https://external-api.kalshi.com/trade-api/v2/events?series_ticker=KXFED&status=open&limit=1)). Some strike codes are offset: the BTC hourly market `KXBTCD-26NOV0518-T87299.99` is the "$87,300 or above" market, its strike encoded as the threshold minus 0.01, and its hour `18` is Eastern time. This is exactly why the numbers must come from `floor_strike` and never from the ticker. Sports markets are `structured`, with `custom_strike: {"basketball_team": "<uuid>"}`. Player props and the multivariate combos (`KXMVECROSSCATEGORY-…`, an opaque hash ticker with `mve_selected_legs`) need the rules text to interpret, and a first integration should skip them.

**Polymarket's hierarchy is Event → Market → two outcome tokens, and which ID to trade depends on the market's ledger version.** Each market has a `conditionId`, a `questionID`, a unique `slug`, and `outcomes` and `outcomePrices` stored as JSON strings inside the JSON, so they must be parsed twice. The tradable ID comes from `clobTokenIds` when `version` is `"v1"` (the Gnosis CTF ledger) and from `positionIds` when it is `"v2"` (the PositionManager ledger). A market is tradable only when `enableOrderBook` and `acceptingOrders` are both true ([Market Details](https://docs.polymarket.com/market-data/market-details.md); [Markets & Events](https://docs.polymarket.com/concepts/markets-events.md)). Multi-outcome events are **negRisk groups**, where a NO in one market converts atomically into a YES in every other. In augmented negRisk events, the docs warn **never to trade the "Other" outcome**, because its meaning shifts as placeholder outcomes get named ([Negative Risk](https://docs.polymarket.com/concepts/negative-risk.md)). What a market pays on lives in the free-text `description`, with `resolutionSource` and `resolutionMechanism` as hints. Crypto up/down markets are the deterministic exception: their slugs are built from the asset, the window and the start time (`eth-updown-15m-1794004200`), and they resolve on a Chainlink 60-second TWAP with no dispute process ([Resolution](https://docs.polymarket.com/concepts/resolution.md); [live gamma events](https://gamma-api.polymarket.com/events?limit=5&closed=false&tag_slug=15M&order=startDate&ascending=false)).

qkt's symbol rules take these codes almost unchanged. A qkt symbol is `VENUE:CODE`, the code must match `[A-Za-z0-9_.@-]`, and the DSL cannot hold `-`. The gateway client therefore maps a venue code by prefix plus `-`→`_`, and maps back by **looking the code up in the gateway's current instrument listing** ([QktSymbols.kt:3-19](../../src/main/kotlin/com/qkt/instrument/QktSymbols.kt); [GatewaySymbols.kt:73-92](../../src/main/kotlin/com/qkt/connector/gateway/GatewaySymbols.kt)). The VGP wire requires a dated contract to stay listed for at least 30 days after expiry so the reverse lookup keeps working ([vgp-v1-wire.md:100-102](../../docs/superpowers/specs/2026-10-01-vgp-v1-wire.md)).

| Venue object | Venue code | qkt symbol | Notes |
|---|---|---|---|
| Kalshi market | `KXHIGHNY-26NOV06-T74` | `KALSHI:KXHIGHNY_26NOV06_T74` | One symbol per market; qkt short = NO |
| Kalshi bucket with a decimal | `KXHIGHNY-26NOV06-B73.5` | `KALSHI:KXHIGHNY_26NOV06_B73.5` | `.` is file-safe; DSL lexer acceptance unverified |
| Kalshi series (backtest root) | `KXHIGHNY` | `KALSHI:KXHIGHNY` | `futures:` root plus catalog |
| Polymarket outcome | slug `eth-updown-15m-1794004200`, outcome "Up" | `POLY:ETH_UPDOWN_15M_1794004200_UP` | Adapter mints the code; token ID stays internal |

The YES/NO representation differs between the two venues, and the difference fits qkt's netting model. On Kalshi, "buy NO at Y" is "sell YES at 1−Y" in a single book, and a position is signed. So **one qkt symbol per market, with a negative position meaning NO**, matches both the venue and qkt's netting simulator exactly. On Polymarket, YES and NO are separate tokens and there is no short selling, so the adapter should list two instruments per market with `trading: long_only`. Jon Becker's finding that NO beats YES at 69 of 99 price levels is a fact about who trades each side, not about different books, so it does not change this mapping ([jbecker.dev](https://www.jbecker.dev/research/prediction-market-microstructure)).

The real symbology problem is that **a new set of symbols appears every day**. Today's qkt has `@front` and `@next` selectors for futures and delta/DTE leg selection for option structures. It has no "the bucket containing X" selector, and `FOR EACH` is substitution at compile time ([structures.md](../../docs/reference/dsl/structures.md); [streams.md:386-401](../../docs/reference/dsl/streams.md)). A `.qkt` file that names `KXHIGHNY_26NOV06_T74` is out of date the next morning. The workaround that leaves core alone is an **event resolver outside qkt**. It walks `/series/{s}` → `/events?series_ticker=&status=open` → `/markets?event_ticker=`, evaluates each market's strike predicate against a rule (for example "every market priced 0.75–0.95 that closes within 36h"), and writes that day's strategy file and catalog rows from a template. A DSL selector such as `OPEN x = EVENT ON KALSHI:KXHIGHNY { BUY YES RANGE CONTAINING fc.value DTE 0 TO 1 }` is the clean long-term answer. It belongs with the `event` kind, not in the first build.

## A spot-kind adapter needs no qkt change; three small core fixes make it exact

**The intended route for any new venue is a `qkt-venue-gateway` adapter reached through qkt's `type: gateway` connector.** The gateway never imports qkt, qkt core may not name a connector, and the kill switch lives in the gateway ([futures-options-design.md:43](../../docs/superpowers/specs/2026-09-30-futures-options-design.md)). An adapter is one module implementing `VenueAdapter`. Its members cover identity, instruments, account and positions, open orders, `place`, `cancel` and `modify` by label, `orderByLabel`, fills, settlements, klines and quotes. The host supplies the SQLite journal, idempotency, reconciliation every 60 seconds, and the kill switch ([VenueAdapter.kt:3-194](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/adapter-api/src/main/kotlin/com/qkt/venuegateway/adapter/VenueAdapter.kt); [design.md:142-200](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/docs/design.md)). One rule acts as a hard gate: `place` must send qkt's `clientOrderId` as the venue's order label, and "a venue without such a field cannot be adapted" ([writing-an-adapter.md:7-16](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/docs/writing-an-adapter.md)). Kalshi passes on paper with `client_order_id`, though lookup by that id still needs confirming. Polymarket has no documented client label. `salt` or the bytes32 `metadata` could carry one, but nothing in the docs says orders can be queried by either.

### The zero-core path today

The VGP `kind` enum is `spot|perpetual|future|option|equity`. The contract testkit asserts that `expiryMs` is present exactly for `option` and `future` ([VenueEnums.kt:3-31](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/adapter-api/src/main/kotlin/com/qkt/venuegateway/adapter/VenueEnums.kt); [ContractChecks.kt:54-67](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/adapter-testkit/src/main/kotlin/com/qkt/venuegateway/testkit/ContractChecks.kt)). A `future` with an expiry would route the instrument through qkt's contract-catalog path, which only knows futures. So the zero-change listing is **`kind: spot`, no expiry, `currency: USD`, `contract_size: 1`, `tick_size: 0.01`, `volume_step: 0.01` (for Kalshi fractional fills), `volume_min: 1`**. On the qkt side, `GatewayInstrumentSpec` builds `InstrumentMeta` for `spot` and `equity` only, so the instrument gets size metadata and passes live symbol checks ([GatewayInstrumentSpec.kt:9-38](../../src/main/kotlin/com/qkt/connector/gateway/GatewayInstrumentSpec.kt)). Resolution is what makes this path work. The adapter emits the wire event `settlement {symbol, price: 0|1, time, costs}`. qkt translates any `WireSettlement` into `ContractSettled`, and `SettlementCloses` closes every strategy holding that symbol at that price with `ExitReason.EXPIRY`. **No code on that path checks `DerivativeTerms`** ([GatewayEventTranslator.kt:165-166](../../src/main/kotlin/com/qkt/connector/gateway/GatewayEventTranslator.kt); [ContractSettlement.kt:8-31](../../src/main/kotlin/com/qkt/app/ContractSettlement.kt); [SettlementCloses.kt:11-37](../../src/main/kotlin/com/qkt/broker/SettlementCloses.kt)). Live fees need no qkt model either: the adapter reports the venue's actual fee as `exchange_fee` on `fill.costs[]`, and qkt books it ([vgp-v1-wire.md:328-339](../../docs/superpowers/specs/2026-10-01-vgp-v1-wire.md)).

The adapter itself absorbs every venue quirk. Market orders become IOC limits at 0.99 to buy and 0.01 to sell, which satisfies the testkit's rule that a market order never rests. Closing is a `reduce_only` IOC. Wire `stop` and `stop_limit` orders are refused with `VenueRefusedException`, because neither venue offers stops on binaries and qkt forwards stops to the gateway instead of holding them ([GatewayOrders.kt:81-122](../../src/main/kotlin/com/qkt/connector/gateway/GatewayOrders.kt)). Strategies must therefore use limit exits or hold to settlement, not bracket stops. Prices are snapped to the market's `price_ranges`. When an order book side is empty, the adapter reports the bid as null, not 0. Resolved markets stay listed for 30 or more days. On Kalshi, `determined` is the settlement trigger (mark at `settlement_value_dollars`) and `finalized` is the cash event. On Polymarket, `market_resolved.winning_asset_id` triggers settlement at 1 or 0, a 50-50 resolution settles at 0.5, and the adapter (or a host job) redeems on-chain.

Five things go wrong on this path, and the plan should name them. First, the instrument carries no expiry, so qkt shows no `dte`, applies no expiry guard, and cannot tell a pending resolution apart from a quiet market. Second, Insights displays the quantity unit as null, because `quantityUnit()` knows nothing about this use of spot ([InsightsVenues.kt:116-126](../../src/main/kotlin/com/qkt/observe/insights/InsightsVenues.kt)). Third, a code ending in `USD` would trigger the base-asset fee logic in `GatewayInstrumentSpec`, so such codes must be avoided. Fourth, the outlier gate in `MarketDataGate` can reject a genuine news jump, such as 0.30 to 0.95, until it re-baselines ([MarketDataGate.kt:5-30](../../src/main/kotlin/com/qkt/marketdata/MarketDataGate.kt)). Fifth, `TickIngest` drops any non-option tick priced at 0 and any tick with a bid or ask of 0 or less ([TickIngest.kt:97-110](../../src/main/kotlin/com/qkt/app/TickIngest.kt)). Polymarket's provisional fills add a sixth problem: the adapter should report a fill only at `CONFIRMED`, or emit a reversal on `FAILED`, because qkt has no notion of a provisional fill.

### Backtesting on the same path

In backtests, a binary contract fits the **dated-future machinery** almost exactly. P&L is `qty × contractSize × Δprice`. `ExchangeSimulator` tracks each contract's expiry, cancels working orders at expiry, and `ExpirySettlement` closes every holder at the catalog's delivery price ([ExchangeSimulator.kt:110-134](../../src/main/kotlin/com/qkt/broker/exchange/ExchangeSimulator.kt); [ExpirySettlement.kt:16-121](../../src/main/kotlin/com/qkt/broker/exchange/ExpirySettlement.kt)). The setup is a `futures:` root such as `KALSHI:KXHIGHNY` with `multiplier: 1`, `tickSize: 0.01`, `expiryGuardHours: 0` and margin `{initial: 1, maintenance: 1, basis: per_contract}`. `per_contract` 1.0 is the conservative stand-in for a short binary's collateral of (1−p), which neither margin basis can express ([MarginTerms.kt:5-32](../../src/main/kotlin/com/qkt/instrument/MarginTerms.kt)). Add a hand-written `contracts/KALSHI/KXHIGHNY.json` with one row per market, carrying its expiry and resolved value, and import prices with `qkt data import --kind ticks|bars` ([ContractCatalog.kt:13-50](../../src/main/kotlin/com/qkt/instrument/ContractCatalog.kt); [import-data.md](../../docs/how-to/import-data.md)). Two gaps make the result biased. **`ListedContract.deliveryPrice` must be greater than 0** ([ContractCatalog.kt:26-28](../../src/main/kotlin/com/qkt/instrument/ContractCatalog.kt)), so every NO resolution falls back to the last traded price, typically 0.01–0.03, with a warning. That systematically flatters losing longs and short-changes winning shorts. And fees can only be approximated: `ContractFeeCommission` is linear in price, so the closest fit is `exchangeFeePerContract: 0.0175`, a fee-maximum upper bound ([ContractFeeCommission.kt:7-46](../../src/main/kotlin/com/qkt/pnl/ContractFeeCommission.kt)).

### Three small, justified core changes

Each of these changes fixes a correctness gap that no adapter or script can work around, and none is named after a venue, which follows the "sources are descriptions" rule.

| Change | File | Why it cannot live outside core | Risk to existing runs |
|---|---|---|---|
| Allow `deliveryPrice >= 0` | [ContractCatalog.kt:26-28](../../src/main/kotlin/com/qkt/instrument/ContractCatalog.kt) | Catalog validation is in core; NO resolutions otherwise settle at a stale price | None: existing catalogs are all > 0 |
| Generic `p·(1−p)` per-order fee model, with a rate and a rounding unit, selectable from root YAML | New `CommissionModel` beside [EquityCostCommission.kt](../../src/main/kotlin/com/qkt/pnl/EquityCostCommission.kt) | Commission models are code, not config ([CommissionModel.kt:7-52](../../src/main/kotlin/com/qkt/pnl/CommissionModel.kt)) | None: opt-in per root |
| Zero price legal for a flagged instrument | [TickIngest.kt:97-110](../../src/main/kotlin/com/qkt/app/TickIngest.kt) | The tick floor is in core | Can wait: adapters and importers can write a missing bid as empty instead of 0 |

The fee model follows the template of `EquityCostCommission`. It accumulates contracts per `orderId` and charges each fill `ceil_to_unit(rate × C_cum × p × (1−p)) − already_charged`, which reproduces Kalshi's per-order round-up. The same model with a 0.00001 rounding unit covers Polymarket, whose rates come from each market's `feeSchedule`. Telling maker from taker needs a role on the fill. Until that exists, a backtest should charge every fill as a taker, which is conservative.

### The clean path: an `event` instrument kind

The full model is a new `DerivativeTerms` subtype, `EventTerms`, plus a VGP kind `event`. It follows the precedent set when equities added a product kind to qkt and VGP: "every existing strategy must backtest to identical trades", and new behaviour arrives only through a new kind ([equities-design.md:84-90,131-140](../../docs/superpowers/specs/2026-10-27-equities-design.md)). `EventTerms` would carry the series root, the event id, the close time, the expected settlement time, an optional `strikeLow`/`strikeHigh`, `outcome`, a mutually-exclusive group, and the formula fee. Price would be bounded to [0, payout], zero would be legal, and margin would be the premium for longs and (payout − p) for shorts. The cost is real. `DerivativeTerms` is sealed, and its KDoc says every consumer's `when` must handle a new subtype; **23 main-source files** pattern-match on `FutureTerms` or `OptionTerms`, including `StrategyCapabilityChecks.kt:101`, `InsightsVenues.kt` and `ExchangeSimulator.kt:114` ([DerivativeTerms.kt:5-22](../../src/main/kotlin/com/qkt/instrument/DerivativeTerms.kt)). On the gateway side, the change touches the VGP spec (the qkt copy is authoritative), `InstrumentKind`, the testkit rule, host wire mapping, and qkt's kind-string switches (`GatewayInstrumentSpec`, `GatewayContractCatalog.kt:29`, `GatewayCollarWiring.kt:31`). Gateway process requires the host and API change to land as its own `feat/` PR before the adapter branch ([adapters.md:9-18](https://github.com/elitekaycy/qkt-venue-gateway/blob/dev/docs/adapters.md)). The DSL additions belong in the same programme: event fields (`dte`, `settles_at`, `settled`), a strike-bucket selector, `norm_cdf`, sizing where risk equals the premium, and an event-level aggregate such as the sum of YES asks. They must use contextual identifiers and new sealed subtypes, because the strategy fingerprint is `sha256(ast.toString())` ([futures-options-design.md:37-42](../../docs/superpowers/specs/2026-09-30-futures-options-design.md)). `OptionTerms` with a digital payoff is the wrong shortcut: options require a positive strike and an index underlying, and they assume Black-76 throughout ([OptionTerms.kt:5-45](../../src/main/kotlin/com/qkt/instrument/OptionTerms.kt); [OptionPayoff.kt:18-26](../../src/main/kotlin/com/qkt/derivatives/options/OptionPayoff.kt)).

## Evidence favours being the maker and buying favourites, not out-forecasting the crowd

**The best-documented edge in prediction markets is structural.** Bürgi, Deng and Whelan studied 46,282 Kalshi contracts from 12,403 events (2021 to April 2025). Buyers of contracts under 10 cents lose over 60% of their money, and contracts above 70 cents earn **small but statistically significant positive returns after fees**. Takers average −31.46% and makers −9.64% (contract-weighted). The bias holds across financials, crypto and weather, and is weaker in politics ([Whelan PDF](https://www.karlwhelan.com/Papers/Kalshi.pdf)). Jon Becker's study of 72.1M Kalshi trades (2021 to November 2025) reaches the same conclusion with volume weighting, which is the relevant measure for capacity: **makers +1.12%, takers −1.12%**. NO beats YES at 69 of 99 price levels, and a 1-cent YES has an expected value of −41% ([jbecker.dev](https://www.jbecker.dev/research/prediction-market-microstructure)). Two caveats limit how much this edge can be relied on. Whelan's 2025 coefficient is "smaller and less statistically significant", and Becker shows the maker/taker sign *flipped* in 2024: takers were ahead in 2021–23, until retail sports flow arrived. Maker fees now also apply on some Kalshi series. The edge is real, it depends on who the other side is, and it is shrinking.

The maker-side evidence on Polymarket points the same way, but the competition is faster. In 2,688 fifteen-minute crypto markets (February 2026), makers won only 47% of fills yet **netted +$728,501 from takers**, and the profitable wallets were near-100%-maker bots plus a few directional "snipers" ([Telonex](https://telonex.io/research/top-crypto-traders-polymarket-15m)). Liquidity rewards pay resting two-sided quotes daily ([Polymarket liquidity rewards](https://docs.polymarket.com/market-makers/liquidity-rewards)). Intra-market "sum-to-one" arbitrage produced about **$40M of realized profit from April 2024 to April 2025**, but the top three wallets took about $4.2M of it. It is a latency race ([arXiv 2508.03474](https://arxiv.org/abs/2508.03474); [EmergentMind summary](https://www.emergentmind.com/papers/2508.03474)). Profits overall are heavily concentrated: under 1% of wallets took about half of politics profits, and a profitable month was followed by another only 41–51% of the time. Copying leaderboard traders has no support in the evidence ([CoinDesk](https://www.coindesk.com/markets/2026/04/29/a-tiny-group-is-winning-on-polymarket-as-under-1-of-wallets-take-half-the-profits); [Vultax](https://vultax.com/research/best-polymarket-traders-leaderboards)).

The popular forecasting theses rest on weaker evidence than their write-ups suggest. On weather, Crosier finds that **Kalshi's implied daily-high forecast beats the best public product (NBM) by about 10% RMSE in 6 of 7 cities, and the NBM moves toward the market four times as far as the market moves toward the NBM**. A bot that simply reads GFS, ECMWF or NBM is trading against people who already have that information ([arXiv 2609.23969](https://arxiv.org/abs/2609.23969)). The most transparent weather-bot log in the notes went 38 wins and 125 losses for +$6.93 ([printmoneylab](https://www.printmoneylab.com/2026/04/weather-bot-episode-14-163-trades-v29-overhaul.html)). Options-implied mapping looks attractive for qkt, which already has Deribit options and Black-76. But the evidence is one week of BTC hourly data (n=162) and an S&P study where the options fair value sat **inside Kalshi's spread 72% of the time**, which means no tradable gap ([kalshi-mispricing](https://github.com/milanroundraise/kalshi-mispricing); [kalshi-implied](https://github.com/anaborne/kalshi-implied)). The NBER macro-markets paper also leaves open whether such gaps are risk premia rather than edge ([NBER w34702](https://www.nber.org/system/files/working_papers/w34702/w34702.pdf)). Cross-venue arbitrage claims are unverified practitioner blog posts, and the venues word "the same" event differently ([dev.to polytrage](https://dev.to/polytrage/why-the-same-market-trades-at-different-prices-on-polymarket-and-kalshi-4l84)).

| Strategy | Evidence | Fits qkt today? | Verdict |
|---|---|---|---|
| Favourite carry (buy 0.70–0.95, hold to settlement) / fade longshots | Two large Kalshi datasets, academic | Yes: limit entry, no exit | **First strategy, on Kalshi** |
| Passive making with rebates and rewards | Data studies, official reward programmes | Partly: qkt is not a quoting engine | Second; needs a recorded L2 book |
| Sum-to-one / negRisk arbitrage | Academic, but won by fast wallets | No event aggregate in the DSL | Skip |
| Options-implied digital vs Kalshi BTC/S&P ladders | Student projects; 72% inside spread | Yes with hub data; no `norm_cdf` | Research only |
| Weather vs NWP | Market beats NBM | Yes via `HUB:` | Avoid |
| Cross-venue, LLM forecasting, copy-trading | Anecdote or negative | n/a | Avoid |

Favourite carry belongs on Kalshi, not Polymarket, because of **resolution risk**. Buying at 0.98 earns 2% per win and loses 98% on one wrong resolution. Polymarket's UMA oracle has produced disputed outcomes on markets worth $237M and $7M, and nine wallets reportedly cast about half of UMA votes. A backtest that reads only final outcomes cannot see this tail ([Decrypt](https://decrypt.co/329210/polymarket-rules-no-237m-controversial-bet-over-zelenskyys-suit); [CoinDesk](https://dev.coindesk.com/markets/2025/03/27/polymarket-uma-communities-lock-horns-after-usd7m-ukraine-bet-resolves); [KuCoin flash](https://www.kucoin.com/news/flash/polymarket-dispute-resolutions-dominated-by-9-whale-addresses-critics-raise-concerns?lang=en_US)). Kalshi resolves from a named source under CFTC rules. Its fallback is still discretionary ("the last fair price determined by Kalshi"), but it is not a token vote ([live series](https://external-api.kalshi.com/trade-api/v2/series/KXHIGHNY)). Today's DSL can already express the strategy: a rule on `ask`, a `LIMIT AT` entry, a fixed `SIZING`, and no exit, so the position rides to the settlement event. A sketch, not yet checked with `qkt parse`:

```qkt
STRATEGY kx_fav_carry VERSION 1
SYMBOLS
    m = KALSHI:KXHIGHNY_26NOV06_T74 EVERY 1m
RULES
    WHEN m.bid >= 0.80 AND m.bid <= 0.94 AND POSITION.m = 0
    THEN BUY m SIZING 20 ORDER_TYPE = LIMIT AT m.bid   -- rest as maker; hold to settlement
```

The event resolver writes one such block per qualifying market each day. This is also why the event-level DSL work can wait.

**The backtest has to be honest about fills and sample size.** Kalshi's free data is 1-minute YES bid/ask OHLC candles, trades, and settled outcomes. Markets settled before a rolling cutoff (2026-09-06 when queried on 2026-11-05) move to `/historical/*` endpoints ([Candlesticks](https://docs.kalshi.com/api-reference/market/get-market-candlesticks.md); [Historical Cutoff](https://external-api.kalshi.com/trade-api/v2/historical/cutoff)). No venue offers historical L2 depth. Oddpool sells Kalshi book snapshots from 2026-03-19 onward ([Oddpool](https://docs.oddpool.com/kalshi/overview.md)). Becker's open dataset covers 2021 to November 2025, but resolved markets only ([GitHub](https://github.com/jon-becker/prediction-market-analysis)). Polymarket's Data API v2 serves price series back to 2022 (12-hour buckets for full life, 15-day windows at finer resolution) plus trades ([Data API v2 OpenAPI](https://data-api.polymarket.com/v2/openapi.json)). The right test design follows from these limits. Run the **taker-at-ask version** first as a lower bound. If it survives the fee-maximum cost, the maker version has room. Treat the maker version as unproven until it has been forward-tested against a self-recorded WebSocket book, because queue position cannot be recovered from candles. Count markets, not days, and cluster by event, because the buckets of one event are perfectly dependent. Apply the fee regime that was in force on each date: Kalshi charged makers from about April 2025, and Polymarket rolled out fees between January and March 2026.

## Ghana makes access, not engineering, the deciding question

**Whether a Ghana resident can open a Kalshi account has not been checked, and the answer blocks everything.** Kalshi announced availability in about 140 countries in late 2025, and in 2026 it entered Brazil (XP) and Canada (Wealthsimple) through partners. A secondary source says its user agreement still restricts 38 countries, and that list was not retrieved ([CDC Gaming](https://cdcgaming.com/brief/kalshi-expands-to-140-countries-announces-funding-5-billion-valuation/); [Bloomberg](https://www.bloomberg.com/news/articles/2026-03-09/kalshi-teams-up-with-brazil-s-xp-for-first-international-push); [dev.to summary](https://dev.to/thesythesis/the-export-5ea)). Funding is the next problem. Free ACH needs a US bank, and USDC deposits through Zero Hash are the plausible route from Ghana, with withdrawal caps that sources disagree on ([BettingHero](https://bettinghero.com/help/kalshi/deposit/how-do-i-deposit-and-withdraw-crypto-on-kalshi)). Kalshi's US legal fights are almost all about sports (losses in the 6th, 9th and 2nd Circuits, a win in the 3rd, a Supreme Court petition pending) ([CNBC](https://www.cnbc.com/2026/09/25/appeals-court-rules-states-can-regulate-sports-prediction-markets.html); [Legal Sports Report](https://www.legalsportsreport.com/285892/us-appeals-court-denies-kalshi-request-for-rehearing/)). A strategy built on weather, economics and crypto avoids most of that risk.

**Polymarket's international venue is technically open from Ghana.** The geoblock list of fully blocked and close-only countries includes the US, the UK, France, Germany, Singapore, Australia and nine African states (BI, CF, CD, ET, LY, SO, SS, SD, ZW). Ghana is not on it, and the API enforces the block by IP ([Geoblock](https://docs.polymarket.com/api-reference/geoblock)). **The server's IP matters as much as the trader's residence.** An adapter running on a host in Germany, the UK, the US or Singapore is close-only and its orders are rejected. The regions of bot1 and bot2 are not recorded in the notes, so they must be checked before an adapter is placed there. Polymarket US is a separate CFTC exchange with Ed25519 auth and its own API, but it requires US KYC, so it is not an option for this user ([US Authentication](https://docs.polymarket.us/api-reference/authentication.md)). The October 2026 CFTC probe into Polymarket's geolocation controls is a reminder that offshore access can tighten without warning ([CNBC](https://www.cnbc.com/2026/10/27/cftc-probes-polymarket-over-2022-settlement.html)).

Two fallbacks deserve a note. **IBKR ForecastEx** can be traded through the standard TWS and Web APIs as `OPT` on exchange `FORECASTX`, with YES as a Call and NO as a Put. It is buy-only and limit-only, so a position is exited by buying the opposite side ([IBKR TWS API](https://www.interactivebrokers.com/docs/tws-api/doc/event-trading/contract-definition-discovery/forecast-ex-contract-example)). Eligibility for a Ghana-resident client is unknown. **Hyperliquid HIP-4** binaries (a daily BTC contract settling against the mark price at 06:00 UTC, fully collateralized) are permissionless and use the same signed-action API as Hyperliquid perps ([Chainstack](https://docs.chainstack.com/docs/hyperliquid-hip4-outcome-markets-trading)). Their liquidity is small next to Kalshi and Polymarket. Betfair's official API IP list does not include Ghana, but third-party lists do, and its back/lay odds model fits qkt worse than a $1 binary ([Betfair developer support](https://support.developer.betfair.com/hc/en-us/articles/28271961503516-Which-IP-regions-are-restricted-from-accessing-the-Betfair-API)).

## Phased recommendation

**Start with Kalshi, on the zero-core path, with favourite carry on non-sports daily series, and let Phase 0 decide whether to switch to Polymarket.** Kalshi's API meets every gateway precondition (an order label, a demo environment, decimal strings, a fee formula exposed per series), its resolution is centralized, and the strongest strategy evidence comes from its data. The research phase needs no account, so it can start while eligibility is being checked.

## Conclusion

The hard part of putting prediction markets into qkt is not the engine. qkt's symbol-generic settlement path, its netting simulator and its gateway architecture already absorb a $1 binary with almost no friction. The honest blockers are outside the code: whether this user can hold an account, whether a venue's orders can be looked up by label, and whether an edge that belonged to makers in 2024–25 survives maker fees and faster competitors in 2026. That ordering should shape the effort. Spend days on eligibility and data before writing an adapter, and spend weeks on the adapter before building a new instrument kind. The `event` kind and its DSL selector are worth designing now and building only after live results justify them.

A second point is easy to miss. Prediction markets reward the opposite of what qkt's research culture has optimised for so far. The gold and crypto work hunts predictive alpha, but the evidence here says the money is in *supplying* liquidity to biased flow and in avoiding resolution tail risk. The most useful strategy work is therefore microstructure: queue position, fee shape, and choosing which side of the longshot bias to stand on. Forecasting matters less. A recorded L2 book from Phase 1 is the asset that makes that work possible, and the venues do not offer one, so start recording it early.
